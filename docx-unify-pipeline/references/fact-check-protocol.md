# 事实核查协议（S5b）

**适用对象：事实性内容——主要是奖项、新闻、官方通报。不含小范围事件。**
一条流水线里最容易出问题的就是这一步：模型很容易"看着像真的就放过去"，
而这类内容恰恰是评审最会去查的。所以流程必须可复核、可反驳。

---

## 1. 范围（先划清，不然会做无用功）

### 要做

| 类别 | 例 |
|---|---|
| **奖项 / 荣誉** | 「获 2023 年度国家科技进步二等奖」「入选 XX 学会优秀博士学位论文」 |
| **新闻 / 公开报道** | 「2024 年 3 月，团队在 XX 会议上发布了……」 |
| **官方通报 / 政策文件** | 「依据《XX 管理办法》（工信部〔2022〕XX 号）」 |
| **机构与人物事实** | 单位全称、职务、任期、部门归属 |
| **数字型公开事实** | 项目编号、批复文号、标准号、专利号 |
| **第三方成果归属** | 「该方法由 XX 大学于 2019 年提出」 |

### 不做

- **小范围事件**：课题组内部的会议、内部测试、未公开的实验安排。
  这类**没有公开来源**，联网也查不到，硬查只会拖垮进度。
- **本文档自身的数据**（自测指标、自建数据集规模）——那是 P10 数据自洽的事，不是事实核查。
- **主观判断**（"效果显著"、"具有重要意义"）——不可证伪，不查。

**判据一句话**：这条断言**有没有可能有一个权威公开来源**？
有 → 查；没有 → 跳过并在核查表里标注 `out-of-scope`，别让它悄悄消失。

---

## 2. 抽取：把正文切成原子断言

从正文里逐条抽出**可证伪的原子断言**，一条只讲一件事。

```
原文：该成果于 2023 年获中国电子学会科学技术奖一等奖，并在 2024 年
       IEEE INFOCOM 会议上作了主题报告。

拆成两条：
  F-001  该成果于 2023 年获中国电子学会科学技术奖一等奖
  F-002  该成果于 2024 年在 IEEE INFOCOM 会议上作了主题报告
```

**不拆的后果**：一条里两个事实，一个对一个错，判定就没法落。
拆完每条都要能填「主体 / 时间 / 事件 / 载体（奖项名/会议名/文号）」四格。

### 抽取时顺手记定位

每条断言记：`序号` + `所在章节` + `段号` + `原文片段`。
段号以**出单时那一版**的指纹为准——这是后面 CRS 的 `where` 来源。

---

## 3. 检索：源的可信度分级

**检索必须用 `WebSearch` 工具，不能凭记忆回答。** 记忆里的奖项名称、届次、
主办单位经常会串（尤其是"二等奖"和"一等奖"、"XX 学会"和"XX 协会"）。

| 级别 | 源 | 用法 |
|---|---|---|
| **一级（权威）** | 政府及部委官网、学会/协会官网、主办单位官网、国标委、专利局、官方新闻稿 | **可直接定案** |
| **二级（可靠）** | 主流媒体（新华社、人民日报、科技日报、中国科学报）、机构官方公众号、会议官网 | 需与一级源或另一二级源**交叉印证** |
| **三级（参考）** | 行业媒体、百科、维基、个人博客、转载稿 | **不可单独定案**，只用来找线索再回溯一级源 |
| **无效** | 无出处的聚合页、AI 生成内容农场、年份对不上的转载 | 直接弃用 |

### 检索规则

1. **至少两个独立来源**（一级源可单独定案）。两个源都在转同一篇通稿 → 算**一个**源。
2. **优先查原始载体**：查奖项就查该奖的官方获奖名单（不去查"某校获该奖"的新闻）。
3. **核对四格**：主体、时间、事件、载体**四个都要对**才对。只对上名字不算证实。
4. **记录 URL + 访问日期**。落进清单时必须是可点击链接。
5. **中文与英文各查一次**（涉及国际会议/期刊/专利时）。

---

## 4. 判定：四态，不含糊

| 判定 | 含义 | 落档 |
|---|---|---|
| `supported` | 有权威来源，四格全对 | `closed`，进「已核」区留档（**不改文档**） |
| `partially_supported` | 主体对但时间/届次/等次/载体有出入 | **S 档**，按来源改正 |
| `contradicted` | 有权威来源且**明确矛盾** | **S 档**，按来源改正，并写明原表述错在哪 |
| `insufficient` | 找不到公开来源，或只有三级源 | **C 档**，标注"未找到公开来源"，**交由老板决定** |
| `out_of_scope` | 属小范围事件，本协议不查 | 不动，只在核查表里留一行 |
| `unverifiable` | 断言本身不可证伪（主观表述） | 不动 |

**`insufficient` 绝不等于错。** 把"查不到"写成"疑似错误"是最严重的一类误报——
它会让老板去改一条本来就是对的内容。

---

## 5. 落成 CRS 行

事实核查的每条结论，按统一 CRS 格式产出一份 `*_事实核查.json`，
再由 `crs_merge.py` 合进唯一清单。

```jsonc
{
  "id": "CR-021",
  "grade": "S",                       // partially_supported / contradicted → S；insufficient → C
  "source": "fact-check",
  "category": "事实",
  "where": {"section": "5.2", "para": 1487,
            "anchor": "中国电子学会科学技术奖一等奖", "count": 1},
  "before": "该成果于 2023 年获中国电子学会科学技术奖一等奖",
  "after":  "该成果于 2023 年获中国电子学会科学技术奖二等奖",
  "basis":  "中国电子学会官网《2023 年度科学技术奖获奖名单》载为二等奖；"
            "https://www.cie.org.cn/... （访问 2026-10-09）",
  "risk": "low",
  "impact": "无",
  "executor": "text_replace",
  "decision": "pending",
  "after_override": null,
  "notes": "四格核对：主体对 / 时间对 / 事件对 / 等次错"
}
```

**`basis` 是硬要求**，必须包含：来源名 + URL + 访问日期 + 核对结论。
没有 URL 的 basis 视为未完成核查。

---

## 6. 核查表（交付给老板看的形态）

除了 CRS 的 json，另出一份人读的 `<文档名>_事实核查表.md`：

```markdown
# 事实核查表 —— <文档名>（访问日期 2026-10-09）

核查 32 条：证实 24 / 部分不符 1 / 矛盾 0 / 无公开来源 5 / 超范围 2

## 一、需要改（1）

| 编号 | 位置 | 原文断言 | 判定 | 权威来源 | 建议改为 |
|---|---|---|---|---|---|
| F-007 | 5.2 · 段 1487 | 2023 年获中国电子学会科学技术奖**一等奖** | 部分不符 | 中国电子学会官网《2023 年度科学技术奖获奖名单》[链接] | 二等奖 |

## 二、未找到公开来源（5）—— 请老板确认

| 编号 | 位置 | 原文断言 | 说明 |
|---|---|---|---|
| F-011 | 3.1 · 段 402 | 「获 2022 年 XX 省科技进步一等奖」 | 省级获奖名单未公开，官网只到 2021 年 |

## 三、已证实（24）—— 无需改动，留档备查

| 编号 | 断言 | 来源 |
|---|---|---|

## 四、超范围未查（2）

| 编号 | 断言 | 原因 |
|---|---|---|
| F-030 | 「课题组 2024 年 6 月内部测试通过」 | 小范围事件，无公开来源 |
```

**「已证实」和「超范围」也要列**。老板看到"我核了 32 条"才会相信"只有 1 条要改"
是认真核出来的，而不是随便挑了几条。

---

## 7. 禁令

1. **不臆造来源。** 宁写 `insufficient`，不编 URL。编出来的链接一打开就是假的，
   比"没查"更伤信任。
2. **不用记忆当证据。** 所有 `supported` 判定都必须有本次检索拿到的 URL。
3. **不擅自改文档。** 事实核查只出清单。改不改、怎么改，老板勾了才算。
4. **不把 `insufficient` 写成"疑似错误"。** 两回事。
5. **不改动「已证实」的表述。** 即使你觉得有更规范的写法——那是 P8 体例的事，
   不要混在事实核查里。
6. **通稿不算独立来源。** 十家媒体转同一篇稿 = 一个源。
