# 长文档编号与交叉引用治理流水线

**这是「治理已有文档」的 skill，不是「生成新文档」的 skill。** 面向的对象是几千段、几十万字、
带公式/图表/目录/清单的中文长文档（技术报告、学位论文、项目申报书、结题报告）。

## 0. 生态位（为什么需要它）

Word 长文档的编号系统由**四层互相耦合的机制**组成，任何一层被手工改过就会全盘错乱：

```
SEQ 域（题注号）→ _Ref 书签（引用锚点）→ REF 域（正文引用）→ TOC 域（图清单/表清单/目录）
                   ↘ 正文里手打的纯文本「图N / 表N」（最脏的一层，完全不受域控制）
```

绝大多数「格式调整」类 skill 做的是 **(a) Markdown → 规范 docx** 或 **(b) 审阅留痕 / 校对 / 对比**；
**没有一个在做「已有 docx 内部的域 + 书签 + 题注编号系统治理」**。本 skill 就是这一层。

与兄弟 skill 的分工：

| Skill | 职责 |
|---|---|
| `docx-formula-image-to-omml` | **工具实现层**：图片公式→OMML、题注/交叉引用/清单/字符级的各类修复脚本，以及 §9–§17 的全部技术细节 |
| **本 skill** | **编排与门禁层**：定义分层顺序、每步断言、验收矩阵、交付纪律；调用上一行的脚本 |
| `docx-format` | **权威实现层**：spec 真源 + `run`/`styles`/`lint`/`revise` + **CRS 协议的唯一实现** |
| `docx-unify-pipeline` | **总编排层**：七阶段 S0~S6；**本 skill 是它的 S2**，被编排调用时的契约见 §9 |

工具实现在 `SKILL_SCRIPTS`（默认 = `~/.workbuddy/skills/docx-formula-image-to-omml/scripts`）。
**开局先确认该目录存在**，不存在就停下告诉用户缺依赖，不要自己另写一套。

## 1. 铁律

1. **先备份**。第一步就是 `cp` 原文件到带时间戳的副本，用户没明说也要做。
2. **只重写 `word/document.xml`**，其余 zip 部件用原 `ZipInfo` **逐字节照抄**。
   这是"没有动过图片/样式/嵌入对象"的唯一硬证据。
3. **先干跑（`--dry`），再写盘**。所有修复脚本必须支持 dry 且 dry 阶段就跑完断言。
4. **每层做完立刻回归**，不要攒到最后一次性验（错位后定位成本翻十倍）。
5. **改完立刻 `ET.fromstring` 逐段验一次 XML**，不要等整篇拼完。
6. **就地覆盖只在验收全绿后做**，并且做完要给出改前备份的 md5。
7. **用户回稿必重跑侦察**。不复用上一轮的结论——Word 重存会改变一切偏移。

## 2. 环境

- Python：`%USERPROFILE%\.workbuddy\binaries\python\envs\default\Scripts\python.exe`（已装 python-docx / PIL）。
- Windows + Git Bash：命令前先修 PATH —— `export PATH="/usr/bin:/bin:/c/Windows/System32:$PATH"`。
- **不要用 python-docx 做修复**（它会把域/书签拍平）。它只用来做最后一步"能否打开"的冒烟。
  修复一律按 `<w:p>` 切分原 XML 做字符串级替换。

## 3. 五阶段流水线

### S0 · 摸底（不做任何修改）

1. **查锁文件**：桌面 `~$<文件名>.docx` 存在、或 `open(path,'r+b')` 抛 `Permission denied`
   → 用户正打开着它，**禁止写回原路径**，只能另存新名。
2. **记指纹**：`size` / `md5` / `word/document.xml` 字符数 / 首个 `w14:paraId`。
3. **判是否被重存过**：与本轮交付件的指纹对比。不同 → 走 §4「半更新」判据，
   **不要直接重跑管线**。

### S1 · 审计（只读，产出证据）

```bash
S=~/.workbuddy/skills/docx-formula-image-to-omml/scripts
python "$S/audit_captions.py"      "文档.docx"     # 题注 / 交叉引用全量审计
python "$S/audit_ref_semantics.py" "文档.docx"     # 按 REF 语义重算，抓「书签过宽」
python "$S/recon_hardref.py"       "文档.docx"     # 正文纯文本「图N/表N」结构侦察
python "$S/build_caption_ref_map.py" "文档.docx"   # (图/表,num) -> _Ref#### 映射
```

四条都要跑。**只看 `audit_captions` 是不够的**——它不查 REF 语义膨胀，也不查硬写号。

### S2 · 分类（七类病灶，逐类定位）

| # | 病灶 | 判据 | 修法 |
|---|---|---|---|
| ① | 题注编号重复 / 跳号 | 段内 `SEQ 图\|表` 的**缓存值**不连续 | 重编号 + 同步 REF 缓存 |
| ② | 硬写题注（编号是死文本，无 SEQ 域） | 题注段无 `instrText` | 补 SEQ 域 + 补 `_Ref` 书签 |
| ③ | 断链 REF / 引用显示号 ≠ 目标号 | `REF` 目标书签不存在，或缓存 ≠ 目标 | 重指向 + 同步缓存 |
| ④ | `_Ref` 书签跨度过宽 | 跨度内既含 `SEQ` 又含 `_Toc` bookmarkStart | 长度守恒地把 `bookmarkEnd` 移到 `_Toc` 之前 |
| ⑤ | 正文纯文本图表号 | 非题注段、非域缓存内的 `[图表]\s*\d+` | 校正编号；或升级为真 REF 域（§3 的 S3-⑨） |
| ⑥ | 图清单 / 表清单编号漂移 | 条目 `PAGEREF _Toc####` 锚点反查的题注号 ≠ 条目显示号 | 按锚点校正（**不要按顺序猜**） |
| ⑦ | 字符级：Unicode 伪角标 / 零宽字符 / 省略号 / 括号 | 见兄弟 skill §13 | 换成真上下标 |

### S3 · 分层修复（固定顺序，每步立刻断言）

```
① 题注重编号（域缓存 + 硬写号）      → 断言 图1..N / 表1..M 连续
② 硬写题注补 SEQ 域                  → 断言 SEQ 图数==图题注数、SEQ 表数==表题注数
③ 断链 REF 重指向 + 显示号同步        → 断言 REF 目标 0 断链、显示号==目标号
④ `_Ref` 书签跨度收窄                → 断言「过宽书签数==0」（判据见 S2-④）
⑤ 正文硬写图表号校正                 → 人工核定优先，其次「同类题注就近 ±12 段」
⑥ 清单缓存重建 + 补 _Toc             → 断言 条目数==题注数、锚点 0 悬空、fldChar 三计数相等
⑦ 字符级（下标/零宽/省略号/括号）     → 断言 subscript 净增数 == 命中数
⑧ REF 语义终检                       → 断言「缓存与语义不符==0」（不能只比 `图 N`）
⑨ 正文纯文本图表号 → 真 REF 域        → 断言 REF 总数 == 基线+命中数、可见文本仅空格变化
```

对应脚本（全部在 `$S`）：

| 步 | 脚本 | 说明 |
|---|---|---|
| ①–③ ⑧ | `fix_cross_refs.py` | 三合一收尾：书签收窄 + REF 缓存重算 + 清单编号按锚点校正。**幂等**，可反复跑 |
| ③–④ | `fix_ref_bookmark_span.py` | 只做书签收窄 + 同步缓存 |
| ①–⑦ | `fix_captions.py` | 题注重编号 + 断链重指向 + 正文硬写号同步 |
| ⑨ | `fix_hardref_to_ref_field.py <in> <out> [--dry]` | 纯文本图表号 → 真 `REF _Ref#### \h` 域 |

**顺序不能换**：③ 依赖 ①（编号定了才有正确目标）；④ 必须在 ③ 之后（否则缓存按旧跨度算）；
⑨ 必须最后（它依赖 ⑨ 之前所有题注号都已稳定）。

### S4 · 验收（一条命令 + 人眼复核）

```bash
python "$S/../../docx-numbering-xref-pipeline/scripts/verify_all.py" "文档.docx" [--base 改前备份.docx]
```
（`$S` 同上 = 兄弟 skill 的 scripts 目录；也可直接用本 skill 的绝对路径
`~/.workbuddy/skills/docx-numbering-xref-pipeline/scripts/verify_all.py`）

`verify_all.py` 一次跑完 13 项机器可验的检查（见 §5）。**`--base` 给了会额外做两版对比**：
可见文本逐段 diff（§5 第 13 条）、结构计数一致（§5 第 11 条）、部件逐字节一致（§5 第 12 条）。
任一项 FAIL → 退出码 2，禁止交付。**第 12/13 条只在给了 `--base` 时才跑**；`--stage s6`
时它们（连同 S6 必然变化的 §5 第 11 条）记 `EXPECT`（预期差异，不计 FAIL，退出码仍 0）。
默认 `--stage s2`，向后兼容。

人眼复核（机器查不了的部分）：让用户在 Word 里 `Ctrl+A` → `F9` 更新全部域，
看编号是否仍然自洽。**这一步才是最终裁决**。

### S5 · 交付

```
--dry 干跑 → 备份 → 写 staged 文件 → verify_all 全绿 → 就地覆盖 → 复查 md5
```

交付话术必须包含：
- 改了哪些（数量 + 分类计数）
- **可见变化清单**（例如"24 处 `图16`→`图 16`"），别让用户自己发现
- 改前备份的路径与 md5
- 一句关键提醒：**域缓存不会自动重算**，插了图表后在 Word 里 `Ctrl+A` → `F9` 一次即可

## 4. 「半更新」判据（用户回稿必查）

用户说"检查一下"，而桌面那份的指纹与交付件全不同时：

1. 先看**锁文件**（S0-1）。
2. 再做**同源性判据**：把两份的**非空段落可见文本**做 `difflib.SequenceMatcher` 序列对齐；
   若只有少量 `replace`/`insert` → 内容同源，只是被重存（Word 会顺手拆合段落、归一化空格、
   重生成 `paraId`）→ **可以安全以干净基线重建**，不会丢用户内容。
3. **典型症状**：一部分域缓存是新值、一部分还是旧值（图清单第 N 条起整体差 1、若干 REF 差 1）。
   既不像"没更新"也不像"已更新" → 就是 Word/WPS 保存时只重算了部分域。
4. 口径：**以自己那份缓存自洽的基线重建**，不要在用户那份上逐条打补丁。
5. 汇报必须说清**哪一份被谁改过**（给 size/md5/时间戳），并说明原文件未被改动。

### 4.1 先分清「Word 另存」和「内容被改」（重要，别误判）

**Word / WPS 走一次「另存为」会必然破坏「部件逐字节一致」**，这与内容对错无关。特征：

| 特征 | 说明 |
|---|---|
| `word/media/*` **被按序重命名** | 例：基线有 `image2.jpeg` + `image3.png`，另存后变成 `image2.png` + `image3.jpeg`（扩展名跟随实际编码） |
| `docProps/app.xml`、`docProps/core.xml`、`word/fontTable.xml`、`customXml/item*.xml`、`word/_rels/document.xml.rels` 被重写 | Word 会重新生成这些元数据 |
| 段落数可能 +N（Word 拆合段落）、`w14:paraId` 全部重生成 | |
| zip 体积回到与"源文件"同量级 | 你的产物因为重新压缩过而偏小，另存会把它顶回去 |

**判据分层**：`verify_all.py` 的 12 号检查（部件逐字节）**只在"刚交付"这个瞬间成立**。
用户动过一次就必然 FAIL —— **不要因此判定"文件坏了"**。真正判断内容是坏还是被改：

- 部件差异**只集中在**上表这些"另存必改"部件 → 同源，正常；
- 出现 `word/media/*` 的**新增/缺失**、`<w:drawing>` 计数变化、段落数变化 →
  **用户确实增删了内容**，此时域缓存一定过期，按 S3 重跑对应层即可；
- `SEQ` 域计数变化 → 题注增删了，**必须重跑 ①②③⑥⑨**。

## 5. `verify_all.py` 的 13 项检查

| # | 检查 | 判据 |
|---|---|---|
| 1 | XML 可解析 | `ET.fromstring(word/document.xml)` 通过 |
| 2 | python-docx 可打开 | `docx.Document(p)` 不抛异常 |
| 3 | 书签配平 | `bookmarkStart == bookmarkEnd` |
| 4 | 域三态配平 | `begin == separate == end` |
| 5 | 域嵌套合法 | 深度扫描：结束深度 == 0、最小深度 >= 0、`separate` 不重复 |
| 6 | REF 断链 / 缓存与语义 | 目标书签存在；`REF x \h` 的缓存 == 按语义重算值 |
| 7 | `_Ref` 书签过宽 | 跨度内同时含 `SEQ` 与 `_Toc` bookmarkStart 的数量 == 0 |
| 8 | 题注编号连续 | 图 `1..N`、表 `1..M` 顺序无重复无跳号 |
| 9 | 清单编号与锚点 | 条目数 == 题注数；每条 `PAGEREF _Toc####` 锚点存在；显示号 == 锚点题注号 |
| 10 | 正文残留硬写引用 | 题注段（含 `SEQ 图/表`）自动跳过；**S3 续表标注段**（整段形如 `续表 N` 或 `图/表 N（续）`，**仅整段完全匹配**）豁免；其余 `[图表]\s*\d+` 一律判为残留硬写引用（应为 0，或列为待办） |
| 11 | 结构计数 | `<w:tbl>` / `<w:drawing>` / `SEQ` 域 / 段落数（给了 `--base` 则逐项对比） |
| 12 | 部件逐字节 + 条目顺序 | **除 `word/document.xml` 外所有 zip 条目逐字节相同 + 条目顺序相同**（**只在给了 `--base` 时才跑**） |
| 13 | 可见文本逐段 diff | **逐段可见文本 diff**（**只在给了 `--base` 时才跑**） |

给了 `--base` 还额外检查（即上表 12/13 两项）：**除 `word/document.xml` 外所有 zip 条目逐字节相同**、
**条目顺序相同**（第 12 项）；**可见文本 diff 仅「图/表与编号之间的空格」变化且去编号骨架不变**（第 13 项）。

**`--stage {s2,s6}` 说明**：默认 `s2`（向后兼容），第 11/12/13 项照常 FAIL。`--stage s6` 是**交付终点**
的验收器——S6 阶段**必然**带来三项与基线不同的差异（插题注段 paras +1、修订模式新增
`word/comments.xml`、段数不同），这时把第 11/12/13 项标成 `EXPECT`（预期差异，显式标注原因、
**不静默**），**不计入 FAIL**，退出码仍为 0。12/13 两项没给 `--base` 时根本不出现在报告里。

## 7. 坑清单（浓缩版，细节见兄弟 skill §10–§17）

0. **域可以跨段落**（TOC 的 `begin` 在「目录」段、entries 好几段、`end` 在最后一条条目段）。
   「某段文字是否在域里」**必须按全篇字符级区间**判断（全篇扫 `fldChar` 用栈算
   `(separate_end, end_start)` 区间，再用 `any(s <= p < e)`）。
   逐段 `q.find(separate)` 会漏判 → 图目录条目被当成正文，把「手打引用」统计和清单全带偏。
1. **域指令会被 Word 拆进多个 `<w:instrText>` run**。实测形态：
   `' SEQ '` + `'图'` + `' \* ARABIC'` 三段，中间夹 `</w:instrText><w:instrText>` 标签。
   → **`re.findall(r'SEQ\s+图', xml)` 这种扫原文的写法会整批漏判**（实测把 20 个 `SEQ 图` 域数成 0，
   连带 19 段真题注被判成「手打题注」、19 处引用全报 MISS）。
   必须按 run 顺序**拼接重建**指令串（用栈按 `begin`/`separate`/`end` 聚合 `<w:instrText>`）。
   坑在隐蔽：换个文档 Word 又把指令合并成一个 run，用正则跑就"正常"，所以别用正则。
2. **域缓存分散在多个 run 时不能按旧偏移逐个替换 `<w:t>`** → 必须一次遍历边拼边写（增量重建）。
   否则报误导性的 `ParseError: not well-formed (invalid token)`。
3. **重建 XML 不能用 `''.join(段落切片)`** → 会丢 `<w:body>`/`<w:table>` 包装，报 `unbound prefix`。
   必须按 `(start, end, newtext)` **倒序区间替换**。
4. **算绝对坐标要用 `<w:t>` 的内文本起点 `m.start(1)`**，用标签起点 `m.start()` 会左偏约 25 字符（静默错误）。
5. **清单编号不要按顺序/标题猜** → 用条目的 `PAGEREF _Toc####` 锚点反查题注号（唯一、无歧义，
   且正文目录条目的锚点是指向章节书签的，天然被排除）。
6. **「缓存文本 == `图 N`」是必要不充分检查** → 必须按 `REF bookmark \h` 语义重算一遍。
7. **`_Ref` 书签必须只包「图/表 」+SEQ 域**（`bookmarkEnd` 落在 SEQ 的 `fldChar end` 之后、
   `_Toc` 的 `bookmarkStart` 之前，相邻不重叠）。包住整段题注 → F9 后引用膨胀成全文。
8. **`paragraph._p.clear_content()`（python-docx）会静默铲掉段落里的书签**（`w:bookmarkStart/End`
   是段落子元素）。凡是"重写题注"的代码，若先 `clear_content()` 再重建，而重建时**没补书签**，
   那么对已有交叉引用的稿子跑一次就会把全部锚点铲平（正文 REF 当场变「错误！未找到引用源」）。
   这是**必然发生**的破坏，不是偶发 → 重写题注必须原地替换或重建时补回书签。
9. **多行 raw-string 拼正则别漏出裸分支**：`r'…|<w:tab |'` + `r'<w:cr/>|…'` 会拆出一个裸 `>`
   分支匹配一切 → 全量误判。用 `<w:br\b|<w:tab\b|<w:cr\b` 单词边界写法。
10. **计数器基线要现算**，别硬编码（一个文档里 REF 可能有 `REF x \h` 与
    `REF x \h \* MERGEFORMAT` 两种 instrText 形态，硬编码会误报）。
11. **用 `find("</w:pPr>")` / `find("</w:rPr>")` 定位「元素结束」必然出错** ——
    `w:pPrChange`（记录**修改前**格式的档案区）内部**还嵌着一份完整的 `<w:pPr>…</w:pPr>`**，
    裸 `str.find` 命中的是**内层**那个。2026-10-10 实测：公式编号对齐执行器据此插入
    「公式前 Tab」，结果 Tab 落进 `w:pPrChange` 里 —— 那是档案区、**不参与排版**，
    段落又被改成 `jc=left` → 17 段公式全部贴左，老板一眼看出。
    正解：**深度计数**（`</?w:pPr>` 扫一遍、配平后取外层终点），`x/tools` 里加了 `ppr_span()`。
    同理适用 `</w:rPr>`（`w:rPrChange`）。
    **且验收脚本必须独立实现同一判据，还要配阳性对照**：当时 `verify_fmt` 第 9 项
    也用裸 `find("</w:pPr>")`，与病灶同源 → 把病灶当合规**假绿放行**（第 0 项"判据自检"
    就是为此加上的：喂好样本须放行、喂坏样本必须被抓）。
12. **REF 域不是一个模子（这是本类任务最容易翻车的地方）**。同一份文档里至少两种 `instrText`：
    `REF _Ref123 \h ` 与 `REF _Ref123 \h  \* MERGEFORMAT`；且**结果区的死文本编号可能跨 run** ——
    `<w:t>-</w:t>` + `<w:t>17</w:t>` 是两个 run。用单一正则（哪怕写得很宽松）实测只命中 **53/64**。
    正解＝**域栈扫描**：`begin` 入栈 / `separate` 置"结果区"标志 / 嵌套域在 `end` 时把结果并入父域 /
    取结果区**最后一个** `<w:t>` 当死文本。⚠️ 判"引用显示值"时**必须合并嵌套域结果**：
    否则 `图` + `-3`（丢了 `STYLEREF 1 \s` 输出的章号）解析不出 `图3-3`，会把一批正常引用判成"异常"。
13. **段落标记 rPr（`w:pPr/w:rPr`）严格来说不是 run 的继承来源**（ECMA-376：它只管段末 pilcrow）。
    历代判据链常把它当继承源，于是"段落级 `ascii=仿宋`""25 处主题字体"这类项**其实本来就已渲染为 TNR**。
    结论：这类项是**残留清理**（为与全篇逐字同构），**不是显示修复** ——
    出单时别写"据此渲染为仿宋"，执行回执要**如实说明"改动不可见"**。
14. **验证器第三个"假红"来源**：`<w:pPr>.*?<w:rPr>` 里的 `.*?` 会**越过 `</w:pPr>`**
    抓到后面 run 的 rPr → 误报"段落标记仍是宋体""263 处非 TNR"。取 pPr **必须深度计数**
    （与第 11 条同源，`ppr_span()` / `get_ppr()`）。
15. **字体判据只认字母会整批漏掉纯数字病灶**。`LATIN = re.compile(r'[A-Za-z]')` 让所有
    纯数字的编号类问题逃过检查 —— 题注编号「33/34」硬写宋体、公式编号「（3-26）」段落级仿宋
    都是纯数字 run。同一份文档，判据从 `[A-Za-z]` 放宽到 `[A-Za-z0-9]` 后由"非 TNR 0 处"变成"39 处"。
    **西文字体判据一律含数字**。
16. **docx 重新打包会改变 deflate 压缩级别**：实测解压后原始字节 219,307,690 → 219,306,884
    （−806 B，就是删掉的那些属性），但压缩包 203.9 MB → 173.2 MB。**体积差 ≠ 内容差**。
    验收口径 = 比**解压后**的逐部件字节；回执须主动解释体积变化（WPS 再另存一次即恢复）。
17. **CRS 里的阿拉伯数字可能是硬编码的粗估值**（`gen_crs*.py` 把"27 处 / 4 个 run / 两处"
    写在字符串模板里）。执行前**必须用脚本重算真实集合**。实测偏差：
    CR-403 单写「4」，真实 12；`Times New Roman Regular` 单写「两处」，真实横跨 7 段 27 个 `rFonts`；
    还漏列了同型邻段。**同型扩展要一并执行，并在回执里显著披露** —— 不能只修单子里点名那一条。

## 8. 格式标杆：把一份文档反向工程成可复用模板

**触发**：用户给两份文档说「第二份是我认为比较完善的版本，希望你以后收到文档就自动调成它的格式
（内容不变），标题 1 / 正文全文调整 + 交叉引用 + 插入题注」。这是一类独立的活：**标杆提取 + 格式对齐**，
不是编号治理，但共用同一套 OOXML 认知。

### 8.1 先比对，别急着提取（这一步经常推翻前提）

跑一遍两份文档的 `styles.xml` 与 `sectPr` 对比。**实测结论：两份文档的样式定义与页面设置可以逐字节相同**，
差异全在域体系。所以「B 比 A 完善」往往指的是：

| 看什么 | 怎么数 |
|---|---|
| styles.xml 样式条数与定义差异 | 按 styleId 抽 rPr/pPr 逐条比对 |
| `<w:bookmarkStart>` 去重计数 | 书签 = 引用锚点 + 目录锚点 |
| `SEQ` / `REF` / `PAGEREF` / `HYPERLINK` 域计数 | 按 run 拼接后分类计数（见 §7 规则 1） |

**别假设「完善版」各方面都更规范**：它可能域体系完整（REF 90 vs 53、书签 250 vs 182），
但段落级直接格式反而更杂（大量覆盖压过样式定义）。

### 8.2 段落级「格式指纹」才是真正的格式（先剥离表格！）

这类文档里绝大多数段落**不用 pStyle**，格式全靠段落级直接格式。所以：

- **必须先剥离 `<w:tbl>…</w:tbl>` 再统计**。实测：OOXML 层面 4698 段，其中 3677 段在表格内 ——
  不剥离的话「正文段落 TOP1」会被表格单元格的 `jc=center + sz=21` 霸占，真正的文档流（1021 段）被淹没。
- 分类后再统计指纹：`heading1/2/3`（按 pStyle 或 outlineLvl）· `body_text` · `caption`（含 SEQ 域）·
  `img`（含 `<w:drawing>`）· `math`（含 `<m:oMath>`）· `empty` · `toc` · `figlist`。
- 每类输出 pPr / 首 run rPr 的 TOP-N 指纹 —— 偏离样式定义的段落会自己冒出来（就是「需要统一」的清单）。

### 8.3 提取模板的两个硬坑

1. **必须解析 `basedOn` 样式继承链**（heading 2 常 `basedOn` heading 1，只覆盖 outlineLvl）。
   合并父子 rPr/pPr 后，**父子属性同现，取「第一个」匹配会拿到父值**。
   实测症状：heading 1 被算成 12pt / 两端对齐 / 首行缩进 2 字符（全是 Normal 的值）。
   → 所有属性提取一律取**最后一个**匹配（子覆盖父）。
2. **标题编号要看它在哪**：若 heading 样式里**没有 `numPr`**、编号是**手打在文本里**（`1.1 概述`），
   模板的 `numbering` 必须设 `null`（不干预）；否则工具补一套自动编号，叠加成「1 1.1 概述」。

单位换算备用：`pt = twips/20`；`cm = twips/566.929`；`line="360" lineRule="auto"` → 1.5 倍；
`firstLineChars="200"` → 2 字符。

### 8.4 题注/引用的标准形状（提取与写入都用这一份）

```
[BM:_Ref####] 图 <SEQ 图 \* ARABIC |缓存> [BMend]   [BM:_Toc####] 标题 [BMend]
```
`_Ref` **只包「图 」+ SEQ 域**，`_Toc` **只包标题**，两者相邻不重叠。跨度写错 → F9 后引用膨胀成整段题注。
图题注在图下方（`caption_position: below`）。标题段落各挂一个 `_Toc####` 书签 —— **目录的前提，清掉就没目录**。

### 8.5 三层对齐（顺序不可换）

1. **样式层**：把标杆的 `Normal / heading 1-3 / caption / toc` 定义移植进目标文档（权威在 styles.xml）。
2. **直接格式层**：按「段落类型 × 标杆指纹」清掉偏离样式的直接格式，让第 1 层真正生效。
3. **域层**：题注 SEQ → 书签 `_Ref`/`_Toc` → 正文 REF → 图/表目录 `TOC \c`（即 §3 的 S3 顺序）。

> 只做第 1 层 = 白做（被直接格式压住）；只做第 3 层 = 危险（见 §7 规则 8/9）。

### 8.6 顺带提醒：工具的误报要识别出来

拿提取出的模板回校标杆自己，报的问题里常常大部分是**工具识别能力不足**造成的假警。
实测 177 项里有 143 项是假警（96 项「公式缺编号」因为编号是手打 `(1)` 文本、47 项「表缺题注」
因为题注是标准 `SEQ 表` 域）。**只有把假警剔掉，剩下的才是真正要改的**，也才能判断模板提取得准不准。

### 8.7 本轮工具（`快速统一docx格式/tools/`）

| 脚本 | 用途 |
|---|---|
| `compare_docx_format.py` | 两份文档的样式层 + 正文层对比（`--section=styles\|doc\|all`） |
| `extract_format_spec.py` | 段落级格式指纹（`--body-only` 先剥离表格） |
| `extract_template_full.py` | 从标杆反推模板 YAML（含继承链解析 + `TemplateSpec` 自校验） |
| `render_docx_report.py` | 把 docx 格式解剖成**单文件可交互 HTML**（概览 / 格式预览 / 段落清单 / 题注与引用），用于「看一眼文档格式化后长什么样」「逐段排查格式」 |

### 8.8 格式报告（HTML）的两条实现要点

给用户「看文档格式化后的样子」时，HTML 报告比 Markdown 表格有效得多。两个必踩的坑：

1. **JSON 注入内嵌脚本前必须转义 `<` → `\u003c`**（U+2028 / U+2029 同理）。
   文档正文里一旦出现 `</script>` 之类的字面文本，直接把脚本截断，页面全白。
2. **「生效格式」要算三层**：合并样式（解析 `basedOn` 链）→ 叠加段落直接格式 → 得到最终值。
   只显示样式定义会漏掉「靠直接格式压过样式」这一大类问题，而那恰恰是最常见的不一致来源。
   报告里要同时标「偏离模板的字段」和「含直接格式覆盖」，两者是不同的病灶。

## 9. 被编排调用时的契约（`docx-unify-pipeline` 的 S2）

本 skill 既可以被老板直接叫起来用，也可以被 `docx-unify-pipeline` 当成**七阶段的 S2**
调用。两种用法**门禁不同、姿态不同**，别搞混：

| | 老板直接调用 | 被编排调用（S2） |
|---|---|---|
| 权威 | 本 skill 自己 | `docx-format` 的 CRS 协议（本 skill 服从） |
| 备份 | 本 skill 自己备份 | **由 S0 统一备份**，本 skill 直接拿现成的备份当 `--base` |
| 出单 | 可以直接修 | **必须先出 CRS**，等老板勾选后才执行分层修复 |
| 闸门 | 验收全绿即可交付 | 验收全绿是 `self` 档闸门；**但写盘仍要老板批准** |
| 账本 | 无 | 每步登记 `pipeline_state.py set/gate/artifact` |

### 9.1 入参

| 参数 | 必填 | 说明 |
|---|---|---|
| `<docx>` | ✅ | **当前阶段的输入**。注意：编排链路里这一份可能是 S1 排完样式后的产物，不一定是原始文件 |
| `--base <备份.docx>` | ✅（被编排时） | S0 的备份。`verify_all.py` 靠它做两版对比 |
| `--out <路径>` | 建议 | 不写则就地覆盖。**被编排时必须给**，链路上的产物要能追溯 |
| `--dry` | ✅ 先跑 | 干跑阶段就要跑完断言 |

### 9.2 出参

被编排调用时，**必须**产出两样：

1. **修复后的 docx** —— 供 S3 继续消费；
2. **编号治理 CRS**（`<文档名>_编号治理.json`）—— 供 `crs_merge.py` 合并进唯一清单。

**这两样要真的产出，不是"心里有数"**。第 2 样的落地方式是
**`scripts/make_crs.py`**（完整用法与三步命令见 §9.7）——它把
S1 审计报告整理出的 `items.json`（已在 `items.json` 里写好 CRS 行的字段，
或由你手工补 `grade/category/where`）转成带指纹、CR-ID 重编号、HTML 勾选页的正式 CRS。
**格式复用 `docx-format` 的 `crs` 模块，不另起一套**，所以能和 lint / polish / facts 的
清单用同一份 `crs_merge.py` 合并。

> 别跳过 §9.7。历史上这里只写"必须产出两样"，结果被编排时**忘了到底用什么命令产出**，
> S2 的 CRS 是手搓的、指纹对不上，S6 落盘时被 `target_md5` 校验打回。

### 9.3 病灶 → CRS 行的映射（S2 七类病灶必须落成 CRS）

§3 的 S2 七类病灶**天然就是 CRS 的行**。每类按统一 schema 落一条，
`executor` 按病灶类型给，`risk` 一律 `high`（动域/书签/编号）：

| 病灶 | `category` | `executor` | `risk` | `after` 怎么写 |
|---|---|---|---|---|
| ① 题注编号重复 / 跳号 | `结构` | `renumber` | `high` | 目标编号序列，如 `图1..N 连续` |
| ② 硬写题注（无 SEQ 域） | `结构` | `add_seq` | `high` | 补 SEQ 域 + `_Ref` 书签（**已有 SEQ 域、仅缺 `_Ref` 书签**的题注 → 由 `scripts/add_ref_bookmark.py` 补建，见 §9.3.1） |
| ③ 断链 REF / 显示号 ≠ 目标号 | `引用` | `fix_ref` | `high` | 目标书签名 + 同步后缓存 |
| ④ `_Ref` 书签跨度过宽 | `结构` | `narrow_bookmark` | `high` | 收窄后的跨度描述 |
| ⑤ 正文纯文本图表号 | `引用` | `hardref_to_ref` | `mid` | 校正后的编号，或"升级为真 REF 域" |
| ⑥ 图清单 / 表清单编号漂移 | `结构` | `fix_toc_cache` | `high` | 按锚点校正后的编号 |
| ⑦ 字符级（伪角标/零宽/省略号/括号） | `体例` | `text_replace` | `low` | 换成真上下标后的文本 |

```jsonc
// <文档名>_编号治理.json 的 item 示例
{
  "id": "CR-011",
  "grade": "S",
  "source": "numbering-xref",
  "category": "引用",
  "where": {"section": "3.4.1", "para": 214,
            "anchor": "如图 45 所示", "count": 1},
  "before": "如图 45 所示",
  "after":  "如图 44 所示",
  "basis":  "该图实际编号为图 44；书签 _Ref00A3 的 SEQ 缓存为 44，REF 缓存为 45",
  "risk":   "high",
  "impact": "同步 REF 缓存；不改书签跨度",
  "executor": "fix_ref",
  "decision": "pending"
}
```

**`where` 必须能被独立复核**：章节号 + 段号 +（图号/表号/书签名/域 ID）。
「第 3 章某处」不算位置。

### 9.3.1 补 `_Ref` 书签执行器（`scripts/add_ref_bookmark.py`）

② 号病灶里有一类**只补书签、不补域**的子情形：题注段**已经有 `SEQ 图`/`SEQ 表` 域**，
但**缺 `_Ref####` 书签**（历史上只挂了 `_Toc` 书签）。这类题注在
`build_caption_ref_map.py` 里反查不到目标，正文引用只能退化成硬写号。由
`scripts/add_ref_bookmark.py`（本 skill 的 `scripts/`，本轮新增的 S2 执行器）补建：

```bash
"$PY" "$N/scripts/add_ref_bookmark.py" <in.docx> <out.docx> [--dry]
```

**与 `fix_ref_bookmark_span.py` 方向相反**，是同一条判据的两个方向：

| 脚本 | 方向 | 何时用 |
|---|---|---|
| `fix_ref_bookmark_span.py`（兄弟 skill `scripts/`） | **过宽 → 收窄** | `_Ref` 已存在，但跨度包住了整段题注（含 `_Toc`） |
| `add_ref_bookmark.py`（本 skill `scripts/`） | **缺失 → 补建** | `_Ref` 根本不存在，题注只有 `SEQ` 域 |

**硬判据（两者共用，口径必须一致）**：新 `_Ref` 跨度的 XML 长度 **< 350**，
且跨度内部**不含** `_Toc` 开头的书签。这两条是**写死不变的**（保持与
`fix_ref_bookmark_span.py` 的收窄判据同一口径）。

`add_ref_bookmark.py` 的**实际行为**：对每个候选题注段算固定跨度并判定；合格的书签照常插入，
**不合格的那段不出书签**；只要**有任何一段不合法**，就**整体跳过、不落盘并报警**
（它**不做**自动"把 `bookmarkEnd` 往前挪"的收窄——那需要人工先把该段跨度收窄，再重跑本脚本）。

**命名规则**：扫全文档既有 `_Ref\d+`，取当前最大编号 **+1** 起递增；
`w:id` 取现有最大 bookmark id **+1** 起递增。写盘时**只有 `word/document.xml` 变**，
其余 zip 部件逐字节照抄、条目顺序不变（与 §1 铁律一致）。

> ⚠️ 注意：**这条与 §8.7 那张表无关**。§8.7 列的是
> `快速统一docx格式/tools/` 里**另一批**脚本的来源，不是本 skill 的执行器。

### 9.3.2 公式编号对齐 / 公式引用 专项执行器

公式的「编号位置」与「正文引用」是两类独立病灶，各有一个**字符串级**专用执行器
（都在本 skill `scripts/`）。只做区间替换、不改 run 顺序，因此不动书签 / 域 / 批注。

```bash
"$PY" "$N/scripts/eq_ref_fix.py"      <in.docx> <out.docx> <approved.json> [--dry]
"$PY" "$N/scripts/fmt_eq_fix.py"      <in.docx> <out.docx> <approved.json> [--dry] [--no-trace] [--cr203 a|b]
"$PY" "$N/scripts/capfix.py"          <in.docx> <out.docx> <approved.json> [--dry] [--author NAME]
"$PY" "$N/scripts/verify_eq_align.py" <docx>          # 只读体检，逐段列出不合规
"$PY" "$N/scripts/verify_capfix.py"   <基准.docx> <交付.docx>   # 题注/引用 14 类 54 项验收
```

| 脚本 | 管什么 | 硬判据 |
|---|---|---|
| `eq_ref_fix.py` | 编号段补 `_KT*` 书签、坏 REF 域复活、手打引用转真 REF 域 | 命中数须等于基线硬断言（90/13/3） |
| `fmt_eq_fix.py` | 编号右对齐 + 标题/题注/西文字体（CR-101~205） | 见下方「三件套」 |
| `capfix.py` | 借号题注 → 标准 `SEQ` 题注、正文 REF 改指、题注样式归位、**第3章编号顺延刷缓存** | 题注总数 = 图 45 / 表 51，编号 1..N 连续 |
| `verify_eq_align.py` | 只读体检 | 同上「三件套」 |
| `verify_capfix.py` | 只读验收（含阳性对照） | 54 项全 PASS |

**`capfix.py` 的三条硬规矩**（2026-10-10 用血换来的）：
1. **顺延必须刷缓存**：插入新题注后，其后题注的 `SEQ` 缓存仍是旧值 → 打开即重号。
   `renumber_ch3()` 按位置重刷全章缓存，**不要指望用户按 F9**。
2. **域 run 有两种形态**：标准模板域 run **无 `rPr`**；另一批**带 `<w:rPr>`**。
   正则须带 `(?:<w:rPr>(?:(?!</w:rPr>).)*?</w:rPr>)?` 可选段，并 **assert 每段恰好命中 1 次**
   —— 否则「没匹配」会被当「已正确」静默放行。
3. **批注部件要重建**：Word 接受全部批注后会**删掉** `comments.xml` / `commentsExtended.xml`
   并摘掉 Content_Types / rels 声明；再加批注必须重建（`rId247`/`rId248`，`styleId 13`）。
   批注区间 `commentRangeStart` 在段首、`commentRangeEnd`+`commentReference` 在 `</w:p>` 前，
   **都必须落在域区间之外**。


**编号对齐的「三件套」**（合规 = 三条全中）：
① 段落 `w:pPr` 里有 `w:tabs`（`center@4153` + `right@8306`）；
② **公式前**有 `<w:tab/>`，位置在**外层 `</w:pPr>` 之后**、首个 `<m:oMath>` 之前；
③ **编号前**有 `<w:tab/>`。

**原理与参数怎么来的**：正文流排成 `[Tab] 公式 [Tab] 编号`，公式由 **center 制表位**居中、
编号由 **right 制表位**贴右边界。制表位数值由页边距直接推出 ——
`right@pos = 纸张宽 − 左边距 − 右边距`，`center@pos = right@pos / 2`
（实测 A4 11906 − 1800 − 1800 = **8306**，其半 = **4153**）。换纸张/换边距只改这两个数。

**为什么不用另外两种流传很广的做法**：
- ❌ `#` 原生编号法（公式末输 `#(2-2)`）：编号进 `m:oMath` 内部，挂在编号 run 上的书签与
  REF 引用全得重挂，且与「全角括号 + 章内编号」体例冲突。
- ❌ 无框三列表格法：视觉最稳，但全文 90 个公式会平添 90 个 `w:tbl`，干扰表格/题注自动编号。
- ⚠️ 也别指望 `m:oMathPara` 的 `m:jc`：本类文档公式**几乎全是内联 `m:oMath`**（实测 212 段里
  `oMathPara` 仅 1 个），制表位法才是一致做法。

### 9.3.3 REF 缓存同步 / 编号字体统一 专项执行器（`scripts/refcache.py`）

**触发场景**：题注顺延或重编号后，**正文 REF 域的结果缓存仍是旧快照**（REF 显示的是上次 F9 的
快照，**不会自动跟随**）。这类病灶**跨章、批量**（实测 64 处 = 图 47 + 表 17，全在第 3 章），
且常与「编号段字体残留」同时出单。单独一个执行器管这两类：

```bash
"$PY" "$N/scripts/refcache.py"        <in.docx> <out.docx> <approved.json> <crs.json> [--dry] [--author NAME]
"$PY" "$N/scripts/verify_refcache.py" <src.docx> <out.docx>     # 独立验收，不复用执行器任何函数
```

| 关键点 | 做法 |
|---|---|
| 定位 REF 域 | **域栈扫描**（§7 规则 12），不用正则 |
| 死文本取值 | 结果区**最后一个** `<w:t>`，形态 `(-?)(\d+)` |
| 正确值的来源 | 反查题注 `_Ref*` 书签 → 该题注 `SEQ` 域缓存（`build_capnum`） |
| 改法 | 只替换死文本那个数字；**域结构（三态与 instrText）/ 书签 / 前后文字全不动** |
| 硬断言 | 命中数 == CRS 声明的数（不符即退码 `4`，**拒绝写盘**） |
| 落盘 | 只改 `word/document.xml`；批注追加进既有的 `comments.xml` / `commentsExtended.xml` |

`verify_refcache.py` 是**独立实现**（自己重写域栈 + `get_ppr` 深度计数），这是"判据不与病灶同源"
的落地（§7 规则 11）—— 它连"REF 显示值"的解析都另写一遍，避免执行器与验收器共享同一个 bug。

> 本执行器与 §9.3.2 一样是**项目专用**（段落号、批注文案、命中数 64/27 写死），归档价值在于
> **写法模式**：域栈扫描 + `ppr_span` 深度计数 + 批注部件重建 + `argv→env→用法退出` 三级回退。

### 9.4 与 S1 的先后关系

**S1（样式基准）与 S2（编号治理）是并行支路**，互不依赖：

- 样式只动 `styles.xml` 与段落直接格式，不碰 `SEQ`/`REF`/书签；
- 编号治理只动 `document.xml` 域的字符区间，不动样式定义。

**但两者都会改 `document.xml`**，所以：

1. 若并行跑，**必须先合并**（`crs_merge.py` 会把两边的 CRS 合成一份），
   **再统一 `revise` 落盘**，不要各改各的然后拼接 zip。
2. 顺序上建议 **S1 先于 S2**：S1 抹直接格式时若把题注段的段落属性改掉，
   S2 之后算出来的书签跨度才是最终值。反过来做，S1 可能把 S2 刚修好的域区间撑开。

|---|---|---|
| 0 | 13 项全绿（`--stage s6` 时 12/13 可为 `EXPECT`） | 记 `set S2 done`，进 S3 |

### 9.6 登记账本（被编排时必须做）

```bash
U=".../docx-unify-pipeline/scripts"

# ... 四条审计 + 分层修复 + verify_all ...
```

`verify_all` 证明"改对了"，老板的批准决定"改不改"。

### 9.7 怎么把 CRS 真正产出（`scripts/make_crs.py`）

§9.2 要求产出 `<文档名>_编号治理.json`，但 §3 的审计脚本
（`audit_captions.py` / `audit_ref_semantics.py` / `recon_hardref.py` /
`build_caption_ref_map.py`）输出的是**人读报告**。中间这一步由
`scripts/make_crs.py` 完成 —— 它是**适配器**，格式与落盘全部复用
`docx-format` 的 `crs` 模块（不另起一套，见「不要做」最后一条）。

```bash
N="~/.workbuddy/skills/docx-numbering-xref-pipeline"

# ① 审计（只读）→ 人读报告，据此整理出改动项清单 items.json
"$PY" "$N/../docx-formula-image-to-omml/scripts/audit_captions.py" "$DOCX"

# ② 改动项 -> CRS（含指纹、CR-ID 重编号、HTML 勾选页）
"$PY" "$N/scripts/make_crs.py" --docx "$DOCX" --items items.json \
     -o "${DOCX%.docx}_编号治理.json" --html "${DOCX%.docx}_编号治理.html"

# ③ 与 lint / polish / 事实核查 的清单合并成唯一清单
"$PY" "$U/crs_merge.py" --docx "$DOCX" --in "${DOCX%.docx}_编号治理.json" \
     --in "${DOCX%.docx}_改动事项.json" -o "${DOCX%.docx}_统一改动事项.json" \
     --html "${DOCX%.docx}_统一改动事项.html"
```

`items.json` 的每条只需 §9.3 那几栏（`grade` / `category` / `where` /
`before` / `after` / `basis` / `risk` / `executor`）。**校验是硬的**：

- `where` 必须同时有 `section` 与 `anchor` ——「第 3 章某处」不算位置；
- `grade` 只接受 `S/A/B/C`；
- 不合规**不产出**，退出码 `2`，并把每一条违规原因打出来。

空清单也会产出一份空单留档（`[warn]`），这样账本上的 `artifact S2` 不会断。

## 不要做
